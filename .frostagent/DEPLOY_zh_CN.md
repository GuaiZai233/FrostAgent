### 0. 询问用户部署方式
在得到明确回答之前，必须暂停后续部署流程，不得自行选择方案和操作。请停下来让用户回答：此项目以何方式部署？
- Docker 部署（推荐）：容器化，文件结构更干净，克隆镜像，无需配置环境，更方便。
- 二进制部署（如果没有 Docker 的话）：获取对应架构的二进制文件并运行，适合轻量部署。
- 源码部署：克隆完整项目，需配置环境、安装工具链，适合高手。

如果用户选择前者，需确保有 Docker 环境；若无，需要让用户安装或询问是否改变方式，必要时你进行帮助。反之，从 1 开始。

### 1. 检查环境与项目

- 检查当前操作系统、CPU 架构、工作目录，以及 Go、Node.js、pnpm 等工具的安装情况。
- 如果当前工作目录已经包含 FrostAgent，直接使用现有项目；否则将仓库克隆到独立目录，不得覆盖已有项目、配置文件或运行数据。
- 在执行部署前，阅读项目当前版本 README_zh_CN.md 及相关文档，以实际源码和文档为准。
- 如果用户关键需求不明确，请先询问清楚；能通过命令和源码确定（如操作系统等）不要重复询问。

### 2. 选择合适的部署方式

- 根据当前操作系统、是否为公网 VPS、管理界面的访问需求，以及 OneBot、AstrBot 等适配器的运行位置，选择合适的网络拓扑。
- 使用项目规定的依赖版本和锁文件，不要擅自升级依赖、删除锁文件或修改与部署无关的业务代码。
- 如果必须修改 Compose 文件或其他配置才能完成部署，先说明修改原因、影响和替代方案，并尽量保留原有配置。

### 3. 安全要求

- 请询问用户是否要将管理面板暴露至公网，如是，请指导用户前置 Cloudflare Access 等控件鉴权。
- 不得未经明确授权修改防火墙、安全组、端口映射，或将管理接口直接暴露到公网。
- 不得关闭项目现有的身份验证、安全限制或 TLS 校验来绕过部署问题。

### 4. 数据与持久化

- 默认优先使用项目支持的 SQLite 配置；只有在确有需要且经过确认时才使用 PostgreSQL。
- 确认数据库文件、Docker Volume 和其他运行数据能够持久化，容器重启不会意外丢失数据。
- 临时停止服务或排查 **严禁执行** `docker compose down -v`。
- 如果发现已有部署或数据，先识别现状；涉及升级、迁移或覆盖操作时，必须先制定备份与回退方案。

### 5. 实际执行部署

请按步骤执行，每一步都检查命令结果，再继续下一步。

1. 准备必要的依赖和配置。
2. 使用支持的方式构建应用或 Docker 镜像。
3. 检查最终生效的 Compose 配置，确认端口、网络、环境变量和持久化设置符合预期。
4. 启动服务，检查容器状态、启动日志和数据库初始化情况。
5. 验证管理界面的实际可访问性，以及所需 WebSocket 端点的监听情况。
6. 对部署失败的问题进行诊断和修复，不要用关闭安全机制、删除数据或盲目重装来掩盖错误。

### 6. 完成首次初始化

FrostAgent 首次启动会初始化默认 SQLite 数据库，但不会自动创建实例。

服务启动后，请继续指导我完成必要的初始化：

- 访问管理界面并创建实例。
- 配置模型供应商、API 凭据和模型路由。
- 根据需要启用实例，并配置 OneBot、AstrBot 或其他适配器的连接。
- 验证实际模型调用及消息处理链路。

如果当前 Harness 无法安全地操作管理界面，或者缺少必要的 Keys，请明确列出需要我手动完成的步骤，不要随意声称成功。

### 7. 最终交付

部署结束后，请给出一份简明的部署报告，至少包含：

- 架构环境、项目版本或 Git Commit。
- 实际采用的部署方式及关键配置（端口号等）。
- 管理界面的准确访问地址。
- 网络拓扑（如有前置反代等中间件）。
- 数据库和持久化数据的位置。
- 尚未完成的项（如模型配置、实例、沙箱、ActionsCat等）。
