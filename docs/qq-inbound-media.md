# QQ 语音、音频与视频

原生 OneBot 收到语音（`record`）、视频（`video`）或扩展名为音频/视频的文件（`file`）
时，处理方式与图片对齐：

1. 模型路由中配置了「多模态（全链路）」时，先由该模型转述内容，转述结果加上
   不可信标记后拼入用户消息，再交给主对话模型。
2. 「多模态（全链路）」为 Disabled、主对话模型勾选了 `audio` / `video` 能力标签时，
   音视频原样作为多模态输入发给主对话模型。
3. 两者都不满足时，模型只看到 `[语音]`、`[视频]` 或 `[文件:…]` 占位符，并收到
   “无法读取”的引导，不会假装听到或看到内容。

引用消息中的音视频同样处理；原样发给主模型时，只有通过安全审查且未被改写的引用才会附带原始音视频。转述结果经过 `MEDIA_RESULT` 来源的 Watchdog 审查，
风险内容会被脱敏或剔除；计费开启时，转述前与识图一样先检查余额。

## 不持久化

音视频字节只在本轮请求的内存里存在，用完即丢弃：不写入数据库、不导入沙箱、
不进入会话 checkpoint 和日志图片缓存。请求日志和面板中的“最近一次实际请求”
只保留 `[audio omitted: …]` / `[video omitted: …]` 占位符（格式、大小、SHA-256）；
入站消息的传输日志和入口安全审查看到的内联 Base64 也会替换为大小占位符。转述请求的用量计入“多模态理解”。
持久化的只有转述文本：群聊消息的转述会显示在面板会话中对应消息下方，
私聊则作为用户消息的一部分保存。

## 读取方式与限制

- 每轮（当前消息加引用）最多读取 4 段音视频，合计不超过 20 MiB；超出部分按无法读取处理。
  内联 Base64 会先按编码长度检查，超限时不会解码。
- 语音通过 `get_record`（`out_format=mp3`）请求网关转码，并使用返回的 Base64。
  QQ 原生语音是 SILK/AMR 编码，通用模型无法解码；网关没有返回转码结果时，
  会回退到消息段自带的下载地址，若拿到的仍是 SILK/AMR 则按无法读取处理。
  NapCat 需要安装 ffmpeg，并开启返回 Base64 的相关配置。
- 视频优先下载消息段中的 QQ 媒体地址，失败时调用 `get_file`。
- 音视频文件与[接收文件](qq-inbound-files.md)使用相同的受信任 QQ 下载域名和下载器；
  网关返回的本地文件路径不会被直接读取。

## API 格式

- OpenAI Chat Completions：音频使用 `input_audio`，视频使用 `video_url`（Base64 data URL）。
- Gemini generateContent：音视频均使用 `inlineData`。
- Anthropic Messages 与 OpenAI Responses 不支持音视频输入：主对话模型即使勾选了 `audio` / `video` 也不会被直接发送音视频；
  配置为「多模态（全链路）」时转述会失败并按无法读取处理。
- 需要流式输出的模型（如 DashScope 上的 Qwen-Omni）暂不支持。
