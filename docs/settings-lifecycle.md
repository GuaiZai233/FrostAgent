# Settings lifecycle audit

Issue: #339. Baseline: main `68597a6` (includes #341 hot behavior fixes and #344 AstrBot removal).

## Inventory and checks

`internal/settingscontract/testdata/lifecycle.tsv` records all 88 catalog keys,
two additional internal global keys, and all 42 new-instance template entries.
Each row records the scope, catalog `RequiresRestart`, instance/control-plane
restart tables, SQL hot classification, frontend field classification, and seed.
`<absent>` means no seeded SQL row; `<empty>` means a stored empty string.

The inventory is test data. Changes require reviewing the owning consumers and
updating the affected assertions; it is never generated by CI or used by runtime
classification. Existing differences below remain visible as separate columns.
Recording them does not settle the product decisions needed to reconcile them.

| Check | Coverage |
| --- | --- |
| `TestSettingsLifecycleCatalogScopesAndDefaults` | Exact catalog membership/restart flags, global/instance/shared membership, both restart tables, actual service store routing, template values and absent versus empty defaults; new unclassified keys fail |
| `TestSettingsLifecycleSQLClassification` | Every inventoried key on insert, replace and delete, including empty values; exact SQL hot tables, scope conflicts, no-op, unknown-key fallback and hot/cold mixed negative controls |
| `settings-lifecycle.test.ts` | Imports actual frontend field metadata and checks every generic hot/reload field and dedicated/hidden classification against the same inventory; new frontend-only keys fail |
| `TestSQLLifecycleExplicitEmptyHotSettings` | Both save and clear entry points preserve the runtime for absent/empty hot settings and distinguish SQL row presence; global constructor keys with empty values still rebuild |
| `TestSQLLifecycleInitializedDefaults` | Newly created SQL instance contains exactly the inventoried seeded values |
| `TestSQLLifecycleManagerApplyAndClear` | Both single-key and draft HTTP entry points, deletion/clear, runtime identity/cancellation, reopened SQL rows, peer isolation, live global controller mode, shared timeout override and inheritance, constructor iteration limit |
| `TestSQLLifecycleMixedDraftSaveClearAndNoop` | Hot instance + global + constructor key in one save; repeated no-op; combined hot update and cold/global clear; code defaults restored |

These tests run through the existing `go test ./...` and web test discovery in
`make ci`; no separate CI target is needed. Key and conflicting layer appear in
failure messages. The earlier behavior, group probability, ActionsCat and scoped
service tests remain complementary consumer-level checks.

| Family | Owning consumers and boundary |
| --- | --- |
| Thinking / poke / names / reply switches / quote trace / bot loop | Adapters use the runtime scope at ingress or reply time; `internal/adapter/thinking/status.go` rechecks its enabled callback; `internal/poke/poke.go` reads cooldown per use. The #341 manager regression checks runtime identity and retained poke cooldown. |

| Chat history / QQ target groups | Recorder and tool permission checks retain getters supplied in `internal/instance/runtime.go`; scope updates are observed on subsequent operations. |
| ActionsCat | `internal/actionscat/client.go` retains a getter for enabled state, endpoint and tokens; request/tool operations read it. Existing manager tests exercise the dynamic tool visibility. |
| Awareness (all nine keys) | `internal/llm/awareness.go` and `internal/proactive/{awareness,quiet_hours}.go` read engine getters while selecting/triggering targets. SQL settings saves currently reconstruct the runtime because these keys are absent from the hot table. |
| Multi-segment reply (two keys) | `internal/llm/msg_guidance.go`, awareness reply formatting and adapters use `replyformat` with a live getter; SQL settings saves currently reconstruct the runtime. |
| Tool switches / balance query / sleep timeout | `internal/llm/tool_settings.go`, `internal/balancequery/config.go`, and `internal/tools/time_sleep.go` read config per operation. Their settings RPC saves currently reconstruct the SQL runtime; dedicated tool endpoints can have different application paths. |
| Compact batch/max/interval, reflection timeout, agent iterations | `internal/instance/runtime.go` reads these while building the compactor, reflector/provider and engine. They must remain cold until those consumers are deliberately changed. |
| Billing configuration (including both prices), embedding, connections | Runtime construction captures billing config and embedding wiring; `wsclient.Load` captures connection settings. Missing catalog restart flags do not make these hot. |
| Sandbox / security mode / control authentication / origins | SQL `ApplyGlobalSettings` refreshes atomic managers where applicable, while auth/origin checks use getters. | Listeners / Alcyone / internal dialogue template | `cmd/app/main.go`, `cmd/app/storage_gateway.go`, and manager construction/application own additional boundaries. The SQL hot table means “no instance rebuild”; it does not establish whether a socket is rebound or a process restart is unnecessary. |

| `ACTIONSCAT_ENDPOINT`, `ACTIONSCAT_MANAGEMENT_TOKEN`, `ACTIONSCAT_DISPATCH_TOKEN` | Catalog says restart, neither restart table contains them, SQL and frontend are hot. Decide how legacy restart metadata should describe the existing dynamic consumer. |

| `BILLING_PROMPT_PRICE_PER_MILLION`, `BILLING_COMPLETION_PRICE_PER_MILLION`, `GROUP_COMPACT_MAX_BUFFER_SIZE` | Catalog omits restart, instance table and SQL classification are cold. Consumers capture these during construction. Preserve the cold behavior while deciding metadata corrections. |

Changing runtime identity/cancellation behavior needs a decision. Sleep timeout's generic frontend field explicitly says hot. |
| Global keys present in both SQL hot and control restart tables | Includes management address/origins, sandbox and authentication fields. These tables serve different application paths. Decide the intended process/control-plane lifecycle semantics before any unification. |

Follow-up tracking: [#345](https://github.com/GuaiZai233/FrostAgent/issues/345). Metadata and hot-table membership stay unchanged. The runtime comparison now
distinguishes an absent key from a stored empty value, honoring the same hot/cold
classification on save and clear.

## Coverage limits

- The inventory checks the 42 seeded defaults, and manager regressions exercise
  cleared iteration defaults and shared inheritance. It does not prove every code
  fallback or every reset-hint string matches its consumer. For example,
  `MAX_CONTEXT_MESSAGES` seeds 20 while its reset hint/code fallback is 50; these
  are separate lifecycle states.
- Dedicated frontend cards are checked for key coverage, not their individual
  status copy or event behavior. Generic fields' hot/reload metadata is checked;
  frontend global/shared label routing and a real browser session are not covered.
- Manager regressions use SQLite. Existing PostgreSQL draft/rollback CI coverage
  is complementary; this change adds no PostgreSQL lifecycle matrix, actual QQ /
  LLM conversation, socket-rebind or process-restart test.
- `BALANCE_QUERY_CONFIG` is catalog-managed but deliberately omitted from
  `ListEnvVars`; its dedicated configuration API is outside this matrix.
- The internal global keys `ALLOW_REMOTE_MCP_MANAGEMENT` and
  `DEFAULT_DIALOGUE_TEMPLATE` remain hidden from the settings catalog/UI.
